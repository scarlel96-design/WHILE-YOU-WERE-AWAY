# 1. 이번 작업의 최우선 목표

이번 작업의 목표는 지금까지 성공한 체크포인트/복구 시스템이 일부 조사 사건에 맞춘 특수 구현이 아니라,

**NPC 사건
→ 전투/추격 사건
→ 구조물 변화 사건
→ 여러 시스템이 동시에 동작하는 복합 사건**

에서도 재사용 가능한 공통 기반임을 검증하는 것이다.

그와 동시에 다음 미완성 핵심을 실제 구현한다.

1. NPC 중심 사건 A/B/C/D/E 복구
2. 전투·추격 사건 A/B/C/D/E 복구
3. 복합 사건 A/B/C/D/E 복구
4. 중요 아이템 소비 트랜잭션
5. 보상 지급 멱등성
6. 필수 구조물 fallback 실제 구현
7. Story Integrity 검사 확대
8. 자연 생존 전체 진행 검증 기반 마련

새로운 스토리 콘텐츠나 최종 아트 제작보다 이것들을 우선한다.

# 3. NPC 중심 사건 복구 검증

NPC가 단순히 서 있는 사건이 아니라 실제 상태 변화가 있는 사건을 선택한다.

반드시 다음 중 여러 요소를 포함해야 한다.

* NPC 위치 이동
* AI 상태 변경
* 대화 진행
* NPC 고유 상태 변경
* 플레이어와의 상호작용
* NPC ↔ NPC 상호작용
* 사건 완료 후 생활 상태 변화

각 사건에서 다음 중단 지점을 테스트한다.

### A — 시작 직전

트리거 충족 후 사건 실행 직전.

### B — 첫 상태 변경 직후

NPC 이동 또는 대화 상태가 최초로 확정된 직후.

### C — 사건 중간

NPC 행동·대화·월드 상태가 일부 진행된 시점.

### D — 완료 직전

실질적인 작업은 끝났으나 `COMPLETED` 확정 직전.

### E — 완료 직후

완료 확정과 저장 직후.

재접속했을 때 확인한다.

* NPC 중복 생성 없음
* NPC 사라짐 없음
* 이전 위치와 새 위치 동시 존재 없음
* 대화 이중 실행 없음
* 상태 롤백 없음
* 완료 후 생활 상태 정상
* 이벤트 연결 토큰 중복 없음

# 4. NPC 고유성 검증

모든 중요 NPC는 월드 내에서 고유해야 한다.

월드 로드 시 다음 모순을 검사한다.

* 동일 스토리 NPC가 2명 이상 존재
* NPC UUID는 저장됐지만 엔티티 없음
* 엔티티는 있지만 NarrativeData에 등록 없음
* 완료 사건 NPC가 이전 사건 위치에 남아 있음
* 사건용 복제 NPC가 영구 NPC로 남음

복구 정책을 명확하게 정의한다.

단순히 UUID가 없으면 새 NPC를 생성하는 방식만 사용하면 중복이 발생할 수 있으므로

**스토리 ID + NPC 역할 + 저장 상태 + 월드 엔티티 존재**

를 함께 확인한다.

# 5. 전투 및 추격 사건 복구

다음에는 실제 엔티티 AI가 포함된 사건을 대상으로 한다.

최소 하나는 다음을 포함한다.

* 사건용 적 생성
* 플레이어 탐지
* 추적
* 경로 변경
* 전투 또는 회피
* 사건 종료 조건
* 임시 엔티티 제거

각 사건에서 A/B/C/D/E 종료를 검증한다.

특히 다음을 집중 확인한다.

* 재접속 후 적 무한 복제
* 이미 처치한 적 재생성
* 추격 종료 후 적 잔류
* AI 상태가 사건과 불일치
* 플레이어 사망 후 추격이 영구 지속
* 차원 이동 후 사건용 적 잔류
* 사건 완료 후 임시 엔티티 정리 실패

# 6. 사건용 엔티티 ownership 강화

모든 사건 전용 엔티티에는 가능한 한 명확한 소유 관계를 둔다.

예:

* ownerEventId
* instanceId
* spawnRole
* lifecycleState

실제 이름은 현재 코드 구조에 맞게 결정한다.

월드 로드 시 다음을 할 수 있어야 한다.

**완료 사건의 잔여 엔티티 제거
ACTIVE 사건의 필수 엔티티 누락 시 안전 재생성
복제 엔티티 발견 시 하나만 보존
잘못된 event instance 소유 엔티티 정리**

한다.

단순 UUID 저장만으로 상태 일관성을 보장하지 않는다.

# 7. 복합 사건 검증

이번 단계의 가장 중요한 검증 중 하나다.

최소 하나의 사건은 다음 요소 중 4개 이상을 동시에 포함해야 한다.

* NPC
* 임시 적
* 구조물 상태 변경
* 중요 아이템
* 조사 기록
* 연출
* 사운드
* 연결 토큰
* 보상

이 사건을 A/B/C/D/E 모든 위치에서 종료하고 재개한다.

복합 사건이 통과해야 현재 체크포인트 프레임워크를 공통 기반으로 인정할 수 있다.

# 8. 프레임워크 문제와 사건별 문제를 반드시 구분

테스트 실패 시 즉시 해당 사건 안에 특수 조건문을 추가하지 않는다.

먼저 다음으로 분류한다.

### Framework Failure

공통 체크포인트, journal, save/load 문제.

### Event Adapter Failure

특정 사건의 저장/복구 구현 오류.

### Entity Lifecycle Failure

NPC·적·임시 엔티티 문제.

### World State Failure

블록·구조물·통로 상태 문제.

### Transaction Failure

아이템·보상 원자성 문제.

### Migration Failure

저장 데이터 변환 문제.

공통 문제라면 반드시 공통 시스템에서 고친다.

# 9. 중요 아이템 상태 모델 구현

스토리 중요 아이템은 단순히

`player inventory contains item`

으로만 판단하지 않는다.

최소 다음 상태를 구분할 수 있도록 한다.

* NOT_DISCOVERED
* ACQUIRED
* HELD
* RESERVED
* COMMITTED
* CONSUMED
* TRANSFERRED
* RETURNED
* RECOVERABLE_LOST

실제 enum은 프로젝트 구조에 맞게 줄이거나 변경할 수 있다.

중요한 것은

**아이템의 존재 위치와 스토리에서의 논리 상태를 분리**

하는 것이다.

# 10. 아이템 소비 트랜잭션

중요 아이템 소비는 가능한 한 트랜잭션으로 처리한다.

권장 흐름:

**VALIDATE
→ RESERVE
→ SAVE
→ APPLY
→ COMMIT
→ CONFIRM**

예를 들어 플레이어가 중요 장치에 아이템을 넣는 경우:

1. 올바른 아이템인지 확인
2. 해당 사건이 아이템을 사용할 권한 확보
3. `RESERVED` 저장
4. 실제 아이템 제거 또는 장치 이동
5. 사건 상태 변경
6. `COMMITTED`
7. 최종 완료 저장

각 단계에서 강제 종료 테스트를 수행한다.

# 11. 아이템 복제·소실 테스트

반드시 다음 상황을 만든다.

* 소비 직전 종료
* 소비 직후 종료
* commit 직전 종료
* commit 직후 종료
* 플레이어 사망
* KeepInventory ON/OFF
* 아이템 바닥 드롭
* 상자 이동
* 인벤토리 가득 참
* 사건 중 청크 언로드
* 사건 중 차원 이동

어떤 경우에도 중요 아이템이

**플레이어 인벤토리에도 있고 장치에도 동시에 존재**

하거나

**양쪽 모두에서 사라져 캠페인이 막히는 상태**

가 되지 않도록 한다.

# 12. 스토리 중요 아이템 복구 정책

중요 아이템이 Minecraft 기본 시스템 때문에 완전히 사라질 수 있는 경우를 고려한다.

예:

* 용암
* cactus
* despawn
* void
* 폭발
* 플레이어 실수

모든 중요 아이템을 무조건 불멸로 만들 필요는 없다.

그러나 캠페인 필수 아이템이라면 다음 중 하나를 제공해야 한다.

* 재발급
* 대체 아이템
* NPC 복구
* 원형 재제작
* 사건 복구
* 다른 해결 경로

**아이템 하나를 실수로 잃었다는 이유로 15시간 월드가 소프트락되는 상황은 금지한다.**

# 13. 보상 멱등성

모든 중요 보상은 고유 지급 기록을 가져야 한다.

예:

`RewardTransactionId`

형태로 관리한다.

보상 지급 조건을 단순히

`if eventCompleted -> give reward`

로 만들지 않는다.

최소 다음을 관리한다.

* 지급 준비
* 지급 성공
* 지급 실패
* 재지급 필요
* 최종 지급 완료

동일 reward ID는 한 번만 확정되어야 한다.

# 14. 보상 테스트

다음 상황을 테스트한다.

* 완료 직전 종료
* 완료 직후 종료
* 지급 직전 종료
* 지급 직후 종료
* 인벤토리 가득 참
* 재접속 반복
* 저장/로드 반복
* migration
* 월드 복사

월드 복사본에서는 정상적으로 각 월드의 기록을 따라가되, 한 월드의 보상 상태가 다른 월드와 공유되지 않아야 한다.

# 15. 필수 구조물 fallback 실제 구현

이번 작업에서는 설계만 하지 말고 최소 하나 이상의 필수 구조물을 대상으로 실제 fallback pipeline을 만든다.

권장 흐름:

**등록된 위치 확인
→ 위치 유효성 검사
→ 실제 구조물 존재 확인
→ 접근 가능성 확인
→ 주변 충돌 확인
→ 기존 대체 후보 탐색
→ 후보 없음
→ 새 안전 위치 선정
→ 대체 생성
→ registry 갱신
→ story link 갱신**

구조물 좌표만 존재한다고 정상으로 판정하지 않는다.

# 16. 구조물 fallback 실패 시나리오

의도적으로 다음 상태를 만든다.

* 등록 데이터만 있고 구조물 없음
* 구조물 절반만 존재
* 진입구가 지형으로 막힘
* 다른 스토리 구조물과 겹침
* 플레이어 건축물과 충돌
* 청크 생성 도중 종료
* 생성 직후 종료
* registry 기록 직전 종료
* registry 기록 직후 종료

복구 후 캠페인이 정상 진행 가능한지 확인한다.

# 17. 플레이어 건축물 보호

fallback 구조물 생성 때문에 플레이어 거점을 파괴하지 않는다.

최소 다음을 고려한다.

* 플레이어 침대 주변
* 반복 방문 생활권
* 등록된 거점
* 기존 스토리 구조물
* NPC 거주 공간
* 플레이어가 배치한 고밀도 블록 영역

완벽한 플레이어 건축 판별이 어렵더라도 안전거리와 충돌 검사를 둔다.

**스토리 구조물 복구를 위해 플레이어 집을 덮어쓰는 것은 FAIL이다.**

# 18. Story Integrity 검사 확대

기존 무결성 검사를 다음까지 확장한다.

* 사건 상태
* 체크포인트
* 연결 토큰
* NPC 고유성
* 중요 아이템
* reward transaction
* 구조물 registry
* 완료 사건의 임시 엔티티
* migration version
* mutually exclusive 선택

예:

* `itemConsumed=true`인데 동일 고유 아이템이 두 개 존재
* `rewardGranted=true`인데 지급 기록 없음
* `eventCompleted=true`인데 필수 NPC가 사건 상태
* 등록 구조물이 존재하지 않음
* 완료 사건의 임시 적이 살아 있음

등을 검출한다.

# 19. 자동 복구와 진단을 구분

무결성 오류를 발견했다고 모든 문제를 자동으로 조용히 수정하지 않는다.

다음 세 종류로 나눈다.

### SAFE_AUTO_RECOVER

명확하게 정상 상태를 판단할 수 있는 경우.

### RECOVER_WITH_WARNING

복구 가능하지만 데이터 이상이 있었음을 기록해야 하는 경우.

### MANUAL_DIAGNOSTIC

자동 판단이 위험한 경우.

잘못된 자동 복구가 플레이어의 정상 진행을 덮어쓰지 않게 한다.

# 20. 자연 생존 전체 진행 검증 준비

이번 작업 후반부터 실제 자연 생존 플레이를 시작한다.

개발용 명령과 순간이동을 최소화하고

→ 복귀

→ 현재 구현 끝 지점**

까지 진행한다.

# 21. 자연 생존 테스트에서 기록할 데이터

아트 revision 증가는 실제 시각 자산 또는 월드 디자인 revision이 의미 있게 변경된 경우에만 한다.

# 28. 저장 포맷 변경 정책

현재 저장 형식은 4다.

새 필드가 추가된다고 무조건 저장 형식을 5로 올리지 않는다.

기존 형식 4에서 하위 호환 가능한 optional field 추가라면 기존 포맷 유지 가능성을 먼저 검토한다.

반대로 의미 변경이나 필수 migration이 필요하면 명확한 이유와 migration 경로를 만들고 포맷을 올린다.

저장 버전 숫자만 불필요하게 증가시키지 않는다.

**0.3.2 기능 후보**

# 31. 테스트 개수보다 테스트 다양성을 우선

테스트 숫자를 늘리기 위한 단순 중복 테스트를 만들지 않는다.

`VERIFICATION.txt`, `DIFF.patch`, 별도 handoff 문서가 있더라도,

**채팅에 출력하는 최종 보고서만으로 새로운 세션에서 바로 작업을 이어갈 수 있어야 한다.**

* 수정 클래스

* 새 필드
* 상태 변화
* 저장 구조 변화
* migration 변화

단순히 “안정화 개선”이라고 요약하지 않는다.

### 기능별 결과표

최소:

| -- | -- | -------- | -: | -- |

# 35. 이번 작업의 최종 성공 기준

이번 작업의 핵심 질문은 하나다.

**“조사 사건에서 성공한 체크포인트 시스템이 NPC·전투·아이템·구조물까지 포함한 실제 캠페인 시스템 전체에서도 안전하게 작동하는가?”**

다음이 가능해야 한다.

NPC 사건 도중 종료해도
→ NPC가 중복되거나 사라지지 않는다.

추격 도중 종료해도
→ 적과 사건 상태가 다시 일치한다.

중요 아이템 사용 도중 종료해도
→ 아이템이 복제되거나 소실되지 않는다.

보상 지급 도중 종료해도
→ 한 번만 지급된다.

필수 구조물이 잘못되어도
→ 기존 월드를 버리지 않고 다른 진행 경로를 확보한다.

이 다섯 축이 실제 게임에서 검증되면 다음 안정화 단계로 넘어간다.
