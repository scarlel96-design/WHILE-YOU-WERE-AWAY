여울 NPC lifecycle의 남은 실제 플레이 예외 표면을 완전히 닫는다.

순서:

1. NPC 실제 청크 언로드·귀환
2. Nether / End 이동
3. 차원 이동 중 프로세스 종료·재접속
4. 실제 Copy-World divergent progression
5. Residence / path / return-light 환경 장애
6. NPC 손상 저장 실제 클라이언트
7. 전체 NPC lifecycle 통합 회귀
8. NPC lifecycle PASS 여부 최종 판정
9. 전부 PASS인 경우에만 첫 복합 사건 진입


======================================================================
2. 기존 사망·리스폰 수정은 회귀 기준으로 고정
======================================================================

현재 새 정책:

미완료 여울 사건
+ 적절한 현장 플레이어 없음
→ 진행 금지 또는 SUSPENDED

완료된 주민 여울
→ 플레이어 부재와 무관하게 주민 생활 가능


이 구분을 유지한다.

다음으로 회귀하지 않는다.

owner=null
→ 항상 사건 진행 가능

또는

플레이어 사망
→ NPC 사건 자동 완료


현재 witness 기준:

- 살아 있음
- spectator 아님
- 같은 차원
- 현장 반경 내 존재

를 사건 진행 조건으로 사용한다.

단, 완료 이후 여울의 독립 생활까지 witness에 종속시키지 않는다.


======================================================================
3. 첫 작업 — 실제 NPC 청크 언로드·재로드
======================================================================

여울의 실제 entity가 존재하는 청크를 직접 언로드한다.

HOME이나 플레이어 청크만 보고 NPC가 언로드됐다고 판정하지 않는다.

반드시 다음 위치를 각각 기록한다.

- 실제 StoryNpc entity 위치
- StoryActorRecord에 저장된 위치
- snapshot 위치
- residence 위치
- current target 위치
- return-light 위치
- 플레이어 위치


테스트 시작 시 각 위치가 어느 chunk인지 기록한다.


======================================================================
4. NPC 청크 언로드를 실제로 증명
======================================================================

다음 순서로 진행한다.

여울 로드
→ entity 존재 확인
→ 사건 checkpoint 확인
→ 여울 실제 entity chunk에서 플레이어 이탈
→ chunk load 상태 확인
→ entity storage unload 확인
→ 최소 충분한 시간 유지
→ 사건 상태 재검사
→ 플레이어 귀환
→ chunk reload
→ 기존 NPC 재연결


단순히 거리가 멀어졌다는 것으로 unload를 주장하지 않는다.


======================================================================
5. 언로드 동안 진행 금지
======================================================================

미완료 사건에서 여울의 entity chunk가 실제로 언로드된 동안
다음이 자동 진행되면 안 된다.

- checkpoint 증가
- 대화 확정
- 이동 완료
- 귀환등 관찰 확정
- event completion
- relationship fact 추가
- current work 전환
- generation 증가
- 새 NPC 생성


특히:

“NPC가 없는 동안 목적지에 도착한 것으로 처리”

하는 형태를 금지한다.


======================================================================
6. NPC 청크 재로드 성공 조건
======================================================================

귀환 후 최소 다음을 확인한다.

- 같은 storyId
- 같은 UUID
- 같은 instanceId
- 같은 generation
- 같은 영구 관계 facts
- 같은 residence
- 적절한 checkpoint
- canonical 여울 정확히 1명
- duplicate StoryNpc 0
- stale generation 없음
- 사건이 정상적으로 이어짐


runtime path 자체가 동일한 프레임부터 복원될 필요는 없다.

영구 의미를 기준으로 안전하게 path를 재구성한다.


======================================================================
7. NPC 청크 언로드와 Actor Missing 구분
======================================================================

다음을 다시 명확하게 검증한다.

NPC entity 조회 실패
≠
Actor 실제 소실


청크가 언로드된 경우:

UNLOADED / SUSPENDED

계열 상태로 취급해야 한다.

confirmed missing 복구 경로로 진입하거나
새 generation을 만들면 FAIL이다.


======================================================================
8. 실제 청크 언로드 반복
======================================================================

가능하면 최소 두 개 이상의 서로 다른 checkpoint에서 수행한다.

권장:

CHUNK-1
- 등장 후 대화 전

CHUNK-2
- 대화 완료 후 실제 이동 중

CHUNK-3
- 완료 후 주민 생활 상태


완료 후 주민의 chunk unload/reload도 최소 한 번 확인한다.


======================================================================
9. Nether 왕복 검증
======================================================================

여울은 현재 whileaway:quiet_city에 존재한다.

플레이어가 Nether로 이동했을 때:

- 여울 dimension 변경 금지
- Nether에 StoryNpc 복제 금지
- generation 증가 금지
- event failure 금지
- event completion 금지
- relationship/history 유지
- current checkpoint 유지 또는 안전 SUSPENDED
- 귀환 후 기존 NPC 재연결


최소 두 checkpoint에서 검증한다.

예:

N1
- 대화 전

N2
- 대화 후 실제 이동 중


======================================================================
10. End 왕복 검증
======================================================================

Nether PASS를 End PASS로 재사용하지 않는다.

실제 End 이동을 별도로 수행한다.

확인:

- quiet_city의 여울 유지
- End에 여울 없음
- duplicate generation 없음
- 영구 관계 사실 유지
- checkpoint 유지
- 귀환 후 사건 정상 재개


======================================================================
11. 차원 이동 + 새 프로세스 재시작
======================================================================

단순 왕복 외에도 최소 하나는 다음 경계를 수행한다.

quiet_city에서 사건 진행
→ 플레이어 Nether 또는 End 이동
→ 현재 프로세스 완전 종료
→ PID 종료 확인
→ 새 Minecraft 프로세스 실행
→ 다른 차원에서 월드 로드
→ quiet_city 귀환
→ 여울 reconciliation
→ 사건 계속


확인:

- 동일 UUID
- 동일 instance
- generation 유지
- relationship 유지
- residence 유지
- canonical 1명
- duplicate 없음


======================================================================
12. 플레이어 차원 이동을 NPC 소실로 해석 금지
======================================================================

플레이어가 다른 dimension으로 이동했다는 이유로:

- 여울 삭제
- 여울 respawn
- 여울 generation 교체
- 여울 플레이어 위치로 이동

하면 FAIL이다.


======================================================================
13. 실제 Copy-World Divergent NPC Progression
======================================================================

NPC 자체의 관계·거주·작업 상태까지 포함하여
실제 원본/복사 월드 독립성을 검증한다.

절차:

원본 Seed 월드 생성
→ 정상 종료
→ 전체 save directory 복사
→ A/B 생성


A에서는:

여울 사건 완전 완료
→ checkpoint 4
→ maintain_return_light
→ 관계/공동 경험 확정


B에서는:

checkpoint 2 또는 3
→ 미완료 상태
→ 다른 current work / event 상태 유지


그 뒤 양쪽을 각각 새 프로세스로 다시 연다.


======================================================================
14. Copy-World 검증 항목
======================================================================

A와 B 사이에 다음이 섞이지 않아야 한다.

- checkpoint
- UUID binding의 월드 의미
- instance state
- generation progression
- residence
- current work
- relationship facts
- shared experience
- completion facts
- Story NBT
- Actor registry


A를 진행하는 동안 B 파일 hash 불변.

B를 진행하는 동안 A 파일 hash 불변.

가능하면 전체 save tree manifest도 비교한다.


======================================================================
15. Residence 장애 검증 시작
======================================================================

그 다음 NPC가 의존하는 환경 조건의 장애를 실제로 검증한다.

이번 목적은 범용 Structure Fallback을 구현하는 것이 아니다.

목적:

“환경 조건이 깨져도 여울의 identity와 영구 사건 사실은 보존되고,
잘못된 자동 완료나 월드 훼손 없이 안전하게 중단/복구되는가?”


======================================================================
16. Residence 상태 분류
======================================================================

최소 다음 의미를 구분한다.

RESIDENCE_VALID

RESIDENCE_TEMPORARILY_BLOCKED

RESIDENCE_UNREACHABLE

RESIDENCE_MISSING

RESIDENCE_CONFLICT


모든 상태를 하나의 false로 처리하지 않는다.

실제 이름은 프로젝트 스타일에 맞춰도 된다.


======================================================================
17. Residence Missing
======================================================================

별도 복사 월드에서 여울의 residence 핵심 요소를 제거한다.

검증:

- 여울 identity 삭제 금지
- 새 여울 생성 금지
- player home을 새 residence로 자동 지정 금지
- 임의 구조물 생성 금지
- 영구 관계 사실 유지
- 사건이 조용히 완료되지 않음
- 명확한 SUSPENDED 또는 diagnostic 상태


원래 환경이 복구되면 안전하게 재개 가능한지 확인한다.


======================================================================
18. Residence Blocked / Unreachable
======================================================================

플레이어 블록을 이용해 실제 이동 경로를 막는다.

NPC가 목표로 갈 수 없는 상태를 만든다.

기대:

- path 재탐색
- 일정 시간 후 safe suspended
- 영구 실패 아님
- 자동 완료 아님
- NPC 순간이동 아님
- 플레이어 블록 파괴 아님


통로를 다시 열면 기존 NPC가 이어서 행동한다.


======================================================================
19. Pathfinding 정책
======================================================================

다음을 구분한다.

TEMPORARY_PATH_FAILURE

CHUNK_UNAVAILABLE

DESTINATION_BLOCKED

DESTINATION_INVALID

DESTINATION_MISSING


모두 동일 timeout 하나로 처리하지 않는다.

다만 이번 단계에서 지나치게 큰 pathfinding framework를 새로 만들지는 않는다.

현재 여울 사건을 안전하게 처리할 최소 공통 경계만 구현한다.


======================================================================
20. 플레이어 건축 보호
======================================================================

환경 복구 또는 NPC 이동을 위해 다음을 하지 않는다.

- 플레이어 블록 자동 삭제
- 벽 강제 파괴
- 임의 발판 생성
- 길 자동 절삭
- 플레이어 집 덮어쓰기


향후 Structure Fallback에서도 이 원칙을 유지한다.


======================================================================
21. Return-Light Missing 검증
======================================================================

현재 여울 사건의 중요한 실제 환경 조건인 귀환등을 검증한다.

다음 상태를 만든다.

LIGHT-1
정상 귀환등

LIGHT-2
귀환등 block 자체 누락

LIGHT-3
좌표는 같지만 잘못된 block으로 교체

LIGHT-4
다시 정상 귀환등으로 복원


LIGHT-2 / LIGHT-3에서:

- 관찰 checkpoint 확정 금지
- 사건 완료 금지
- 영구 관계 사실 조작 금지
- 새로운 귀환등 임의 생성 금지


LIGHT-4에서 정상 재개해야 한다.


======================================================================
22. Return-Light는 단순 Trigger Block이 아니다
======================================================================

상위 설계 v0.4에서 귀환등은 장기적으로 중요한 복선·관계 소재가 될 수 있다.

따라서 현재 기능 구현에서도 단순히:

block exists = true
→ event done

수준으로 모든 의미를 묶지 않는다.

최소:

- 실제 위치
- 구조/블록 상태
- 관찰 여부
- event context
- NPC 상태

를 구분한다.

이번 단계에서 장기 복선 콘텐츠까지 구현할 필요는 없다.


======================================================================
23. 환경 장애 중 Save/Reload 검증
======================================================================

Residence 또는 Return-Light가 잘못된 상태에서:

→ 저장
→ 종료
→ 새 프로세스
→ 재접속

해도:

- 빈 NPC 상태 생성 금지
- 사건 처음부터 재시작 금지
- 완료로 오판 금지
- canonical 1명 유지


환경을 정상 복원한 뒤 다시 저장/재접속하고 사건 재개를 확인한다.


======================================================================
24. NPC 손상 저장 실제 클라이언트 검증
======================================================================

현재 NPC 저장 probe는 PASS지만
실제 손상 월드 클라이언트는 NOT TESTED다.

이번 단계에서 반드시 대표 범주를 실제 Minecraft에서 검증한다.


최소 세 종류 권장:

CORRUPT-N1
- residence 필수 정보 누락

CORRUPT-N2
- 완료된 NPC인데 required permanent fact 누락

CORRUPT-N3
- completion / current work / relationship 사이 의미 모순


가능하다면 한 종류의 recoverable 사례와
두 종류 이상의 unrecoverable 사례를 둔다.


======================================================================
25. NPC 손상 저장 Fail-Closed
======================================================================

손상된 NPC 기록을 읽었을 때:

“여울이 아직 등장하지 않은 상태”

로 변환하지 않는다.

특히 금지:

완료 여울 손상
→ Actor 0
→ 새로운 여울 등장
→ 사건 처음부터 시작


Load Guard 원칙을 그대로 유지한다.


======================================================================
26. NPC 손상에서 복구 우선순위
======================================================================

복구 판단 우선순위:

1. NPC identity
2. 영구 shared experience
3. relationship facts
4. residence decision
5. 사건 checkpoint
6. current work
7. runtime path/animation


낮은 우선순위 정보를 복구하기 위해
상위 영구 사실을 추정으로 덮어쓰지 않는다.


======================================================================
27. NPC 손상 자동 복구 범위 확대는 보수적으로
======================================================================

현재 Actor load-guard와 같은 철학을 적용한다.

SAFE_AUTO_RECOVER

RECOVER_WITH_WARNING

MANUAL_DIAGNOSTIC


NPC 손상도 이 분류를 사용할 수 있다.

모든 corruption을 자동 수리하는 것이 목표가 아니다.

잘못된 자동복구보다 명확한 차단이 낫다.


======================================================================
28. 완료 후 여울의 생활 상태 검증
======================================================================

사건 완료 이후 여울은 퇴역 Actor가 아니다.

주민으로 남는다.

현재 작업:

maintain_return_light


완료 후:

- 청크 언로드
- 차원 이동
- 프로세스 재시작
- 플레이어 사망
- 복사 월드

을 거쳐도 완료된 주민 상태를 유지해야 한다.


======================================================================
29. 완료 NPC가 Witness 부재로 SUSPENDED되지 않게 주의
======================================================================

미완료 사건의 witness gate와
완료 주민의 자율 행동을 혼동하지 않는다.

완료된 NPC의 일상 routine은:

“근처에 플레이어가 있을 때만 존재”

하는 구조가 아니어야 한다.

성능상 실제 ticking이 정지할 수는 있지만
서사적으로 NPC가 사건 미완료 상태로 되돌아가면 안 된다.


======================================================================
30. Permanent / Current / Ephemeral 구분 재검증
======================================================================

NPC 상태는 최소 의미적으로 다음 세 계층으로 관리한다.


PERMANENT

- identity
- 만남
- shared experiences
- relationships
- 주요 선택
- residence decision
- 사건 완료 사실


CURRENT

- current work
- current target
- current routine
- 현재 목적지


EPHEMERAL

- current path nodes
- look direction
- animation frame
- temporary timer


재접속 때 EPHEMERAL을 정확히 복원하려고
영구 저장 구조를 오염시키지 않는다.


======================================================================
31. NPC↔NPC 관계 확장성 최소 자동 검증
======================================================================

현재 관계 키:

npc:doyun

같은 NPC 대상도 표현할 수 있다.

이번 단계에서 대규모 NPC 사회 시스템을 구현하지 않는다.

다만 최소한:

Yeoul → Doyun 관계 record
저장
→ reload
→ 동일 key/value/history 보존

정도의 serialization round-trip을 추가할 수 있다.

33. NPC Integrity 확대

- missing identity
- invalid residence

- completed + pre-event current work
- unfinished + post-completion facts
- relationship duplication
- impossible checkpoint/work combination
- missing return-light dependency
- actor generation mismatch
- NPC write-guard active
- suspended reason


진단 코드는 가능한 한 고유하게 한다.

Story Integrity

→ 캠페인 Story Integrity 문제


이번 단계에서 과도한 architecture refactor는 하지 않는다.

39. NPC가 PASS되면 첫 복합 사건으로 진입

FIRST COMPLEX CAMPAIGN EVENT

NPC
+ Actor
+ Structure
+ Evidence
+ Scene

가 한 사건 안에서 동시에 움직여도:

- 저장 가능
- 중단 가능
- 재접속 가능
- 중복 실행 방지
- aftermath 유지

가 되는가?

- 장소 상태 변경
- evidence 해석 상태 변경
- 다음 사건 조건 생성


사건 종료 후 모든 것이 원상복귀되는 구조는 금지한다.


======================================================================
43. 아직 중요 Item Transaction은 섞지 않는다
======================================================================

중요한 유일 아이템의 영구 소유권 처리는
별도 Item Transaction 단계에서 봉인한다.

첫 복합 사건에서 필요하다면:

- evidence marker
- 임시 story token
- 비소유권 테스트 도구

정도로 사용한다.

유일 중요 아이템이 반드시 필요하다면
Item Transaction을 먼저 구현한다.

ROLLBACK

배포용 JAR을 롤백 시험으로 파괴하지 않는다.

- save downgrade
- NPC 월드 downgrade
- 데이터 마이그레이션 역변환

65. 그 다음 정확한 시작점
======================================================================

NPC lifecycle이 PASS된 즉시 다음 작업은:

FIRST COMPLEX CAMPAIGN EVENT


첫 복합 사건은 최소:

실제 NPC
+ Story Actor 또는 위협/환경 Actor
+ 실제 장소/구조 상태
+ Evidence
+ Sound/Scene trigger

중 4개 이상을 실제로 연결한다.


목적은 화려한 장면을 만드는 것이 아니라:

“여러 실제 게임 시스템이 동시에 작동하고,
중간 종료·재접속·저장·Aftermath까지 안전하게 이어지는가?”

를 증명하는 것이다.
