======================================================================
1. 이번 작업의 핵심 목표
======================================================================

이번 단계의 목표는 새로운 NPC 콘텐츠를 추가하는 것이 아니다.

이미 구현된 실제 캠페인 NPC 여울이 다음 상황에서도:

- 중복 생성되지 않고
- 사라지지 않고
- 잘못된 세대로 교체되지 않고
- 사건을 중복 완료하지 않고
- 영구 관계 기록을 잃지 않고
- 현재 행동 상태만 안전하게 복원하며
- 완료 후 실제 주민으로 계속 존재

하도록 NPC lifecycle을 봉인한다.


이번 단계의 최종 목표 문장:

“여울은 플레이어 사망, 청크 언로드, 차원 이동, 재접속, 월드 복사,
환경 장애 상황에서도 동일한 캠페인 인물로 유지되며,
영구적인 관계·경험 사실과 일시적인 행동 상태를 혼동하지 않는다.”

2. 현재 확보된 NPC A/B/C/D/E를 회귀 기준으로 고정
======================================================================

현재 여울 사건 흐름:

등장 예약
→ 실제 등장
→ 플레이어 상호작용
→ 실제 이동
→ 귀환등 관찰
→ 사건 완료
→ 새로운 생활 상태


체크포인트:

0 / PREPARED
- UUID
- instance
- 거주지
- 목표
- 작업 예약

1 / PHASE_1
- 실제 등장
- 상호작용 대기

2 / PHASE_2
- 만남
- 대화
- 관계 기록 확정
- 이동

3 / RESOLVING
- 목적지 도착
- 실제 귀환등 관찰 확정

4 / COMPLETED
- 정착
- 공동 경험
- 연결 기록
- 새로운 작업 상태


현재 A/B/C/D/E PASS를 새로운 변경으로 깨뜨리지 않는다.

이번 작업 마지막에 핵심 회귀를 다시 수행한다.


======================================================================
3. 가장 먼저 플레이어 사망·리스폰 검증
======================================================================

보고서에서 다음 첫 작업으로 지정된 항목이다.

여울 사건의 여러 checkpoint에서 플레이어를 실제로 사망시킨다.

최소 다음 경계를 검사한다.


CASE D1

여울 등장 전/등장 예약 이후
→ 플레이어 사망
→ 리스폰
→ 사건 재개


CASE D2

여울 실제 등장 후
→ 아직 대화 전
→ 플레이어 사망
→ 리스폰


CASE D3

대화·관계 사실 확정 후
→ 이동 도중 사망
→ 리스폰


CASE D4

귀환등 관찰 전후 경계
→ 플레이어 사망
→ 리스폰


CASE D5

사건 완료 후
→ 플레이어 사망
→ 재접속
→ 여울의 완료 후 생활 상태 확인


KeepInventory:

- OFF
- ON

두 조건을 모두 실제 Minecraft에서 검증한다.


======================================================================
4. 플레이어 사망의 의미
======================================================================

플레이어 사망은 자동으로 다음을 의미하지 않는다.

- NPC 사건 실패
- NPC 퇴장
- NPC 삭제
- 새로운 generation 생성
- 관계 초기화
- 대화 취소
- 영구 경험 삭제
- 사건 완료
- checkpoint 강제 증가


플레이어 사망은 필요한 경우:

ACTIVE
→ SUSPENDED

또는 현재 NPC runtime의 동등한 일시중단 상태로 처리한다.

영구 사실은 유지한다.


======================================================================
5. 리스폰 위치가 멀리 떨어진 경우
======================================================================

리스폰 지점이 사건 지역에서 충분히 멀리 떨어진 경우도 별도로 검사한다.

예:

플레이어가 도시에서 사망
→ 원거리 Overworld spawn 또는 침대에서 리스폰


기대:

- 여울 사건 자동 완료 금지
- 여울 자동 삭제 금지
- 여울을 플레이어 옆으로 순간이동 금지
- 새 여울 생성 금지
- generation 증가 금지
- 사건 runtime 일시중단
- 플레이어가 다시 돌아왔을 때 안전 재개


======================================================================
6. NPC 실제 청크 언로드 검증
======================================================================

HOME 청크만 확인해서는 안 된다.

다음 위치를 각각 확인한다.

- 여울 실제 entity 위치
- 여울 snapshot 위치
- 여울 residence 위치
- 현재 목표 위치
- 귀환등 위치
- 플레이어 위치


여울이 존재하는 실제 청크가 언로드되는 상황을 만든다.

최소:

NPC 청크 로드
→ 실제 이동/행동 확인
→ 플레이어 충분히 이탈
→ NPC 청크 실제 언로드 확인
→ 일정 시간 유지
→ 재접근
→ 여울 재로드


확인:

- 같은 UUID
- 같은 instance
- 같은 generation
- 같은 storyId
- canonical 여울 정확히 1명
- checkpoint 보존
- 영구 관계 facts 보존


======================================================================
7. 청크 언로드 중 Runtime 시간 처리
======================================================================

NPC가 언로드된 동안 다음이 멋대로 진행되지 않아야 한다.

예:

- path 이동 완료
- 귀환등 관찰
- 대화 완료
- 생활 작업 완료
- event timer 증가
- 새 routine 선택


특히 “NPC가 안 보이는 동안 사건이 해결됐다”는 결과가 나오지 않게 한다.

다만 영구적인 월드 시간과 관계없이 진행되어야 하는 별도 시스템이 실제로 있다면
그것은 명시적으로 설계해야 한다.

이번 여울 사건은 임의 offline progression을 추가하지 않는다.


======================================================================
8. NPC 청크 언로드와 Missing Actor를 혼동하지 않는다
======================================================================

기존 Actor canonical recovery 원칙을 그대로 적용한다.

NPC를 조회하지 못함
≠
NPC가 실제 소실됨


청크가 언로드된 여울을:

missing Actor
→ 새 generation 생성

으로 처리하는 회귀가 없어야 한다.


======================================================================
9. Nether 이동 검증
======================================================================

사건 도중 플레이어가 Nether로 이동한다.

최소 두 checkpoint 이상에서 수행한다.

예:

A.
대화 이전

B.
대화 후 이동 단계


기대:

- 여울 Overworld 유지
- Nether에 복제 NPC 생성 금지
- 사건 영구 실패 금지
- generation 증가 금지
- 관계 facts 유지
- 플레이어가 Overworld로 돌아오면 정상 재개


======================================================================
10. End 이동 검증
======================================================================

Nether와 별개로 End도 실제 검증한다.

Nether PASS를 End PASS로 간주하지 않는다.

확인:

- 여울의 dimension 유지
- 다른 차원에 복제되지 않음
- event checkpoint 유지
- current work / residence 유지
- 귀환 후 canonical 여울 1명


======================================================================
11. 차원 이동 중 종료·재접속 복합 경계
======================================================================

단순 왕복만 검사하지 않는다.

최소 하나는:

Overworld 사건 진행
→ Nether 또는 End 이동
→ 프로세스 종료
→ 새 프로세스 실행
→ 다른 차원에서 시작
→ Overworld 귀환
→ 여울 복구

까지 수행한다.


======================================================================
12. 실제 NPC Copy-World Independence
======================================================================

현재 Actor copy-world independence와 별개로
NPC의 관계·거주지·작업·사건 진행이 서로 독립적인지 실제로 검사한다.


원본 A:

여울 사건 완료
→ maintain_return_light
→ 관계/공동 경험 확정


복사본 B:

checkpoint 2 또는 3에서 중단
→ 다른 진행 유지


그 후 양쪽을 각각 새 프로세스로 재접속한다.


확인:

A의 완료가 B에 전달되지 않음

B의 미완료가 A를 되돌리지 않음

- UUID 처리 독립
- generation 독립
- instance 상태 독립
- relationship facts 독립
- residence 독립
- current work 독립
- story NBT 독립


한쪽 월드를 진행하는 동안 다른 월드 파일이 변경되지 않는지도 hash로 확인한다.


======================================================================
13. 완료 후 NPC 생활 상태 재검증
======================================================================

여울 사건 완료 후:

check_return_light
→ maintain_return_light

로 바뀐다.

이 current work는 영구적인 historical fact가 아니다.

반대로 다음은 영구적으로 유지되어야 한다.

- 플레이어와 만났음
- 공동 대화를 했음
- 귀환등 사건을 경험함
- 정착 사실
- 공동 경험 관계
- 필요한 연결 기록


완료 후:

- 재접속
- 사망
- 청크 언로드
- 차원 왕복

을 거쳐도 이 구분이 유지되는지 검사한다.


======================================================================
14. NPC의 현재 작업은 변경 가능해야 함
======================================================================

앞선 시험에서 이미 current work를 permanent fact로 오판한 테스트가 있었다.

같은 실수를 production integrity에 넣지 않는다.

NPC 상태를 최소 개념적으로 구분한다.

IDENTITY / PERMANENT

- NPC identity
- storyId
- 중요한 경험
- 관계
- 선택
- 약속
- 거주 결정


CURRENT STATE

- 현재 작업
- 현재 목적지
- 현재 path
- 현재 look target
- 현재 interaction target


EPHEMERAL RUNTIME

- animation
- pathfinding 내부 상태
- 순간적인 행동 timer


모든 것을 NBT에 영구 사실로 굳히지 않는다.


======================================================================
15. 거주지 누락 실제 검증
======================================================================

여울의 저장된 residence가 가리키는 위치가 실제로 존재하지 않거나
의미적으로 사용할 수 없는 경우를 별도 복사 월드에서 검증한다.

상황 예:

- residence block 일부 제거
- 핵심 지점 누락
- 구조 자체 미생성
- residence reference가 유효하지만 실제 접근 불가능


자동으로 플레이어 집을 residence로 바꾸지 않는다.

자동으로 주변 블록을 삭제해서 공간을 만들지 않는다.


======================================================================
16. Residence 장애 분류
======================================================================

최소 다음처럼 분류한다.

RESIDENCE_VALID

RESIDENCE_TEMPORARILY_BLOCKED

RESIDENCE_MISSING

RESIDENCE_CONFLICT

RESIDENCE_UNREACHABLE


모두 동일하게 “새 집 생성”으로 처리하지 않는다.


======================================================================
17. 통로 봉쇄 검증
======================================================================

플레이어가 NPC 이동 통로에 블록을 설치한 경우를 검사한다.

Minecraft에서는 플레이어가 월드를 수정할 수 있으므로
기존 path가 막혔다고 사건이 영구 파손되면 안 된다.


검증:

- 일시적 path 재탐색
- timeout
- safe fallback
- 사건 중단 가능성
- 플레이어가 길을 다시 열면 재개


금지:

- 플레이어 블록 임의 삭제
- 벽을 뚫고 순간이동
- 장애 발생 즉시 사건 완료
- 장애 발생 즉시 NPC 재생성


======================================================================
18. 귀환등 누락 검증
======================================================================

현재 사건에서는 귀환등 블록이 실제로 존재해야 관찰 단계가 진행된다.

따라서 다음을 별도 검사한다.

A.
귀환등 정상 존재

B.
귀환등 임시 누락

C.
귀환등 위치는 있지만 다른 블록으로 변경

D.
귀환등이 복원됨


기대:

B/C에서는 사건이 영구적으로 잘못 완료되지 않는다.

D에서 정상 재개 가능해야 한다.


======================================================================
19. 귀환등 문제를 Structure Fallback으로 지금 확대하지 않는다
======================================================================

이번 단계에서 귀환등 하나가 없다고 전체 Structure Fallback 시스템을 앞당겨 구현하지 않는다.

현재 목적은:

“필수 환경 조건이 충족되지 않았을 때 사건을 안전하게 멈추거나 진단한다.”

까지다.

일반적인 필수 구조물 재생성/Fallback은 뒤 단계에서 별도로 구현한다.


======================================================================
20. NPC 손상 저장 실제 클라이언트 검증
======================================================================

현재 NPC 저장 probe에서 다음 6종 의미 손상 차단은 PASS다.

하지만 실제 손상 월드 클라이언트는 NOT TESTED다.

대표 사례를 실제 Minecraft에서 검증한다.

최소 후보:

- residence 누락
- invalid residence
- 완료 NPC의 required permanent fact 누락
- current work 의미 모순
- relation/history 모순
- 조기 completion/link 기록


전부 실제 클라이언트로 만들 필요는 없지만
대표적인 recoverable/unrecoverable 범주를 선택한다.


======================================================================
21. NPC 손상도 빈 NPC 상태로 초기화 금지
======================================================================

기존 StoryStorage Fail-Closed 원칙을 유지한다.

손상된 여울 저장
→ “그냥 여울이 아직 등장하지 않은 상태”

로 초기화하면 안 된다.


특히:

완료한 여울의 저장 일부 손상
→ 사건 처음부터 재시작

은 매우 위험하다.


======================================================================
22. NPC 손상 시 영구 사실 우선
======================================================================

복구 가능한 경우 복구 우선순위:

1. identity
2. 영구 경험
3. relationship
4. residence decision
5. checkpoint
6. 현재 작업
7. ephemeral runtime


현재 path나 look target을 살리기 위해
영구 관계 사실을 희생하지 않는다.


======================================================================
23. NPC 관계 키 저장 구조 재검증
======================================================================

현재:

player 관계뿐 아니라
npc:doyun

같은 NPC 상대도 표현 가능하다.

이번 단계에서 대규모 NPC 사회 시스템을 구현하지 않는다.

다만 serialization / round-trip / integrity 기준으로:

NPC A → NPC B

형태가 실제로 손실 없이 보존되는지 최소 자동 검증을 추가할 수 있다.


======================================================================
24. 관계를 단일 호감도 점수로 축소하지 않는다
======================================================================

향후 관계 시스템은 최소 다음 개념 확장 가능성을 유지한다.

- trust
- closeness
- agreement
- shared experiences
- promise
- conflict
- current goal
- future consensus


이번 단계에서 전부 구현할 필요는 없다.

현재 데이터 구조가 단일 affection int에 고정되지 않도록 유지하는 것이 중요하다.


======================================================================
25. NPC 사건의 재상호작용 검증
======================================================================

사건 완료 후 플레이어가 여울에게 다시 상호작용할 때:

- 완료 사실이 재기록되지 않음
- relationship event 중복 없음
- 공동 경험 중복 없음
- checkpoint 재진입 없음
- Actor generation 변경 없음


현재 일부 검증이 되어 있지만 예외 테스트 뒤 다시 확인한다.


======================================================================
26. NPC 예외 안정화 PASS 조건
======================================================================

다음이 모두 통과해야 npc-lifecycle exception bundle을 PASS로 바꿀 수 있다.

- A/B/C/D/E 최신 회귀
- 사망/리스폰 KeepInventory OFF
- 사망/리스폰 KeepInventory ON
- 원거리 리스폰
- NPC actual chunk unload/reload
- unloaded NPC ≠ missing Actor
- Nether round-trip
- End round-trip
- dimension + process restart
- copy-world divergent progression
- residence missing 안전 처리
- residence blocked 안전 처리
- path blocked 안전 처리
- return light missing 안전 처리
- return light restore/recovery
- 대표 NPC corruption actual client
- 완료 후 생활 상태 재접속
- relationship/history 중복 없음
- canonical 여울 1명
- generation 안정성


하나라도 필요한 실제 검증이 빠지면 PARTIAL 유지.


======================================================================
27. 테스트를 위한 임의 순간이동 최소화
======================================================================

이번 검사는 자동화된 실제 Minecraft 테스트이므로
테스트 준비용 player 위치 이동은 허용한다.

하지만 NPC 자체를 목표 지점으로 강제 teleport해서
pathfinding 성공을 대신하지 않는다.

실제 경로 이동을 검증한다.


======================================================================
28. Pathfinding 실패 자체도 정상적인 게임 상황으로 본다
======================================================================

Minecraft NPC AI에서는 path가 항상 성공한다고 가정하지 않는다.

다음을 구분한다.

- 일시적 path failure
- chunk unavailable
- destination blocked
- destination invalid
- destination permanently missing


이들을 전부 같은 timeout 하나로 처리하지 않는다.


======================================================================
29. Player absence와 NPC absence를 구분
======================================================================

플레이어가 사건 장소를 떠난 것과

NPC entity가 로드되지 않은 것은

서로 다른 상태다.

플레이어 부재:

사건 일시중단 가능

NPC 청크 부재:

entity lifecycle 복구 대상


둘을 하나의 boolean으로 합치지 않는다.


======================================================================
30. NPC 예외 봉인 이후 첫 실제 복합 사건으로 진입
======================================================================

NPC 예외 묶음이 완전히 PASS되면
그때 처음으로 “복합 사건” 구현 단계로 이동한다.

단, NPC 안정화가 PARTIAL이면 넘어가지 않는다.


======================================================================
31. 첫 복합 사건의 목적
======================================================================

첫 복합 사건은 콘텐츠 양을 늘리기 위한 사건이 아니다.

여러 기반 시스템이 실제 캠페인에서 동시에 연결돼도
저장·재접속·중단 복구가 가능한지를 검증하는 사건이다.

최소 4개 이상의 실제 서브시스템을 사용한다.


권장 구성:

- 여울 또는 다른 실제 캠페인 NPC
- Actor / threat
- 실제 Structure state
- Evidence / clue
- Sound / scene trigger

가능하면:

- temporary story item

까지 포함할 수 있다.


======================================================================
32. 아직 중요 Item Transaction을 섞지 않아도 됨
======================================================================

중요 아이템의 영구 소유권 transaction은 뒤 단계에서 별도로 봉인한다.

따라서 첫 복합 사건에서 아이템을 사용한다면:

- 비소유권형 임시 도구
- 단순 evidence marker
- 테스트용 story token

등으로 제한할 수 있다.


중요한 유일 아이템을 사용하고 싶다면
Item Transaction을 먼저 구현해야 한다.


======================================================================
33. 첫 복합 사건에서 금지할 구조
======================================================================

다음처럼 하나의 boolean으로 축약하지 않는다.

complexEventDone=true


대신 실제 단계별 의미를 저장한다.

예:

EVENT_PREPARED
NPC_PRESENT
EVIDENCE_FOUND
STRUCTURE_STATE_CHANGED
THREAT_STARTED
RESOLUTION_COMMITTED
AFTERMATH_ACTIVE


정확한 상태 이름은 사건 설계에 맞춘다.


======================================================================
34. 복합 사건에는 반드시 실제 Aftermath가 있어야 함
======================================================================

사건 완료 후:

NPC 상태
장소 상태
Evidence 상태
다음 사건 조건

중 최소 일부가 실제로 달라져야 한다.

“컷신 끝 → 모든 상태 원복”

형식으로 만들지 않는다.


======================================================================
35. 최신 공포 설계 v0.4를 복합 사건부터 점진 반영
======================================================================

첨부된 최신 설계 v0.4는 계속 상위 기준이다.

핵심:

- 정체성은 현재에서 달라질 수 있는 권리
- 연속기는 사람보다 관계와 빈자리 보존
- 마지막 하루는 합성된 과거
- 기록관은 인간 비상규칙의 누적
- 일곱 형체는 단순 일곱 희생자가 아님
- No-Spawn
- No-Stinger
- Free-Look
- Causality
- Persistence
- Recontext
- Three Lives Location
- Signature Setpiece
- NPC 독립 생활


이번 NPC 예외 검증 단계에서는 신규 공포 콘텐츠를 억지로 추가하지 않는다.

복합 사건 진입 이후부터 작은 규모로 설계 원칙을 적용하기 시작한다.


======================================================================
36. 억지 공포 연출 금지
======================================================================

다음은 핵심 공포 수단으로 사용하지 않는다.

- 이유 없는 뒤쪽 스폰
- 풀스크린 얼굴
- 비명 효과음만으로 놀라게 하기
- 불 끄고 즉시 괴물 출현
- 메모 읽은 직후 뒤에서 공격
- 강제 카메라 회전
- 플레이어 건축 강제 파괴
- 가짜 오류창 반복


주요 장면은 가능하면:

No-Spawn
No-Stinger
Free-Look

세 기준을 함께 목표로 한다.


======================================================================
37. 공포 활성화 시스템은 아직 본 구현 보류

→ LATENT / CONTACT

공포 활성화 저장 필드나 Horror Director를 앞당기지 않는다.

42. Terra 제한 시험을 시작해도 되는 작업
======================================================================

이번 단계부터 모델 라우팅의 아주 제한적인 실제 시험은 가능하다.

단, 핵심 코드가 아니라 명세가 완전히 확정된 반복 작업에만 사용한다.


Terra 후보:

- GPT-6가 확정한 NPC 예외 GameTest 추가
- 동일 정책의 반복 fixture 구현
- 사망/청크/차원 smoke harness 보강
- serialization round-trip 테스트
- 정형 Integrity assertion 추가
- 반복 로그 코드


Terra가 정책을 새로 정하도록 하지 않는다.


======================================================================
43. Luna 사용 후보
======================================================================

Luna는 더 제한적으로 사용한다.

후보:

- 테스트 fixture 데이터 생성
- 반복 상수 등록
- 단순 boilerplate
- 결과 manifest 생성
- 명세가 고정된 표/로그 데이터 처리


실제 게임 행동이나 저장 의미를 판단해야 하면 Luna 사용 금지.

44. 모델 라우팅을 실제로 시험하는 경우
======================================================================

가능하면 이번 작업에서 딱 하나의 저위험 반복 작업을 골라 시험할 수 있다.

권장:

“GPT-6가 NPC 사망/청크/차원 예외 명세와 핵심 코드를 확정한 뒤,
Terra가 동일 명세에 따른 추가 반복 테스트를 구현”

이 정도다.


Caveman과 모델 변경을 동시에 시험하지 않는다.


======================================================================
45. 모델 변경 때문에 작업 중단 금지
======================================================================

모델 전환은 독립적인 하위 작업 경계에서만 한다.

예:

GPT-6
→ NPC 청크 정책 구현
→ 빌드/핵심 테스트 PASS
→ Terra가 추가 반복 테스트 구현
→ GPT-6 전체 검수

가능.


다음은 금지:

GPT-6가 NpcEvents.update 수정 중
→ 중간 상태에서 Terra 전환
→ 나머지 수정


모델 변경 자체를 이유로 사용자에게 중간보고하지 않는다.

46. Terra/Luna 적용 범위 확대 원칙

다음이 여러 작업에서 누적 확인될 경우에만 확대한다.

- 첫 시도 성공률이 GPT-6 대비 문제 없음
- 요구사항 누락 없음
- 테스트 품질 저하 없음
- GPT-6 최종 검수 수정량이 매우 적음
- 재작업 증가 없음
- 버그 유입 없음
- 장기 프로젝트 연속성 문제 없음
- 실제 전체 사용량 감소


조건을 충족하면 이후:

테스트
→ 명확한 adapter
→ 단순 serializer
→ 고정 명세 구현

순으로 조금씩 범위를 확대할 수 있다.

52. 첫 복합 사건의 품질 게이트
======================================================================

- 재접속 복구 가능

- aftermath 존재

53. Important Item / Reward는 아직 별도 단계
======================================================================

복합 사건이 PASS된 뒤:

Item Transaction

다음:

Reward Transaction

으로 이동한다.


Transaction은 이전에 정한:

VALIDATE
→ RESERVE
→ PERSIST
→ APPLY
→ COMMIT
→ CONFIRM

구조를 기준으로 한다.


======================================================================
54. Structure Fallback은 그 이후
======================================================================

Item/Reward 이후에:

필수 구조물 fallback

을 진행한다.

NPC 거주지 장애 테스트를 수행한다고 해서
이번 단계에 범용 Structure Fallback을 섞지 않는다.

NPC 예외 봉인

→ Item Transaction
→ Reward Transaction
→ Structure Fallback
→ 통합 Integrity
→ 자연 생존 전체 진행


자연 생존 테스트 이전까지는
개발 명령/테스트용 이동을 사용할 수 있다.

단, 자연 생존 PASS처럼 보고하지 않는다.
